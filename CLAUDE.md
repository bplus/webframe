# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

Webframe is a Go module (`github.com/bplus/webframe`) — a component library for server-rendered web UIs. It's consumed as a dependency by other Go projects. It is **not** a standalone application; the demo app exists only for development/showcase purposes.

## Commands

```bash
make build          # templ generate → tailwind compile → go build ./cmd/demo
make generate       # templ generate (produces *_templ.go from *.templ)
make css            # npx @tailwindcss/cli -i static/css/input.css -o static/css/output.css
make dev            # go run ./cmd/demo (serves on :3333)
make check          # check-generate → check-vet → check-test → check-ui
make check-generate # templ generate → css rebuild → drift check on *_templ.go and output.css
make check-vet      # go vet ./...
make check-test     # go test ./...
make check-ui       # go run ./cmd/wflint ./demo (UI lint: app code may only compose components)
make ui-check       # Playwright: load /items and / at 390 and 1280, fail on horizontal overflow or console errors; needs `make dev` running, not part of check
npx playwright install chromium   # one-time, before the first ui-check (Playwright's own Chromium, ~170 MB)
go test ./...       # run all tests
go test ./components/copybutton/...  # single package
```

Build order matters: templ generate must run before CSS compilation or Go compilation.

## Architecture

**Component pattern**: each component lives in `components/<name>/` containing:
- `<name>.templ` — template with a `Props` struct and templ component function
- `*_templ.go` — generated Go (committed to git, do not hand-edit)
- Optional: `helpers.go`, `*_test.go`

**Props convention**: components accept a Props struct with `ID`, `Class`, `Attributes templ.Attributes` fields plus component-specific fields. Variadic `...Props` with zero-value defaults is common.

**Key utilities** (`utils/`):
- `TwMerge(classes...)` — always use this to combine Tailwind classes, never concatenate
- `EscapeJS(string)` — use for values injected into JS string literals
- `SanitizeColor(string)` — use for user-provided CSS colors
- `If[T]` / `IfElse[T]` — conditional helpers for templates
- `ScriptURL(path)` — appends cache-busting `?v=` timestamp

**JS integration**: Alpine.js for client-side reactivity (inline `x-data`/`x-on`), HTMX for server-driven interactions (`hx-*` attributes). A global `htmx:afterSwap` listener reinitializes Alpine on dynamic content.

**CSS**: Tailwind v4 with custom theme tokens in `static/css/input.css`. Light (Observatory) is the default palette; dark is an opt-in stored preference.

**Demo app** (`cmd/demo/` + `demo/`): HTTP server on :3333 with the showcase gallery, the traffic stream page (`/traffic`, a `streampage`), the sign-in and error pages (`/signin`, `/signed-out`, `/forbidden`, `/errors/{code}`) and the Items app on a second, sidebar-layout `appshell.App`: `/items` list, `/items/{id}` detail, `/items/new` and `/items/{id}/edit` forms, `/dashboard` (`dashboardpage` with a `timeline` and a `cardgrid`), `/settings` (`settingspage` with a Danger zone in `After`), `/browse` and `/browse/{id}` (`splitpane`). It is the acceptance scenario for the page layer: page declarations and handlers in `demo/*_handlers.go`, no markup of its own. `/sidebar` redirects to `/items`; unknown paths and wrong methods render `errorpage` through the documented ServeMux wrapper. Routes also include HTMX interaction demos (click counter, search, validation, toasts) whose handlers render templ fragments in `demo/pages/fragments.templ`.

Headings: `layout.Section` defaults to an h2 and `panel` to an h3; set `Level` to nest them. `formfield.Feedback` is swapped with `hx-swap="outerHTML"` targeting `#`+`Field.FeedbackID()` (innerHTML nests the wrapper and duplicates its id). `form.Form` is the `<form>` element app code uses (wflint forbids a raw one): inside it, `Required` puts `required` on the control and the browser enforces it; for `TypeSelect` the submitting control is a hidden input the browser never validates, so there `Validate` or a server-side `Error` is the enforcement. A required `autocomplete` inside a form blocks submit until an item is picked (`setCustomValidity` on the text box while the hidden value is empty).

**List pages:** the handler calls `listquery.Parse(r, opts)` to get a `Spec`, applies it to its data (`listquery.Apply` for a slice; `Spec.Offset()`/`Limit()` for SQL), declares a `listpage.Props` (header, filters, columns, rows, the `Spec`, `Total`) and calls `listpage.Respond(w, r, title, p)`. Sort headers, filter changes and page links are all htmx GETs to the same URL that swap only the results region (`listpage.Results`, id `ID+"-results"`) and push the URL; `Respond` serves that region alone when the request's `HX-Target` names it, the page body for any other plain htmx request, and the full document otherwise (`appshell.RenderParts`). DELETE and bulk handlers that fire from inside the list parse the `Spec` with `listquery.ParseCurrent` (the `HX-Current-URL` header's query: the page the user is looking at) and answer with `listpage.RespondResults`, which sets `HX-Replace-Url` to the served state so the address bar follows a clamped page. Every results-only response (`Respond` and `RespondResults`) carries, after the results, out-of-band copies (`hx-swap-oob`) of the filter bar's hidden `sort`/`dir`/`per` inputs and of the intro line, so a sort chosen from a table header survives the next filter change and the intro's counts follow a delete. The filter bar carries `sort`, `dir` and `per` as hidden inputs (never `page`), so a filter change keeps the sort and lands on page 1; when any column is `Sortable` the `sort` input is instead a Sort select (`PhoneOnly`, so visible below md where a `Hidden` sortable column has no header to click): "{Label} ↑" and "{Label} ↓" per sortable column, the ↓ option setting `dir` through `data-tui-filterbar-set-dir`, the option for the Spec's default order submitting nothing (value "" and dir ""), and a leading "Default order" option when no sortable column is the current sort; the out-of-band copy after a header click replaces the select too, so headers and select never disagree, and a list with sortable columns but no filters or search still gets the bar (`md:hidden` as a whole, no "Clear filters"); its URL rewrite drops its own parameters and `page` (`filterbar.Props.Drop`) before writing the current values, so a cleared filter leaves the address bar; the empty state's "Clear filters" drives the bar's own reset (`window.tui.filterbar.reset`) so the controls clear with the results. `listquery` caps `page` at `listquery.MaxPage` (2^31-1) so `Offset()` cannot overflow.

**Form pages:** declare a `formpage.Props` (sections of `formfield.Field`, `Action`, `HxPost: true`) and call `formpage.Respond`; create and edit are the same declaration with different `Values`. On a failed POST the handler sets `Values` from the submitted form and `Errors` by field name and calls `Respond` again, which answers 422 Unprocessable Entity. htmx 2 leaves the target alone on a 4xx by default, so `appshell.Document` ships an `htmx-config` meta that makes error responses swap like 2xx ones (204 still swaps nothing; `htmx:responseError` still fires): the server decides what an error looks like, and the status code stays truthful. The same rule is what lets a 409 whose only body is a toast, or a 404 answered by `errorpage`, reach the page from an htmx request. A raw Go 500 (plain text) does not swap since batch 4 (`htmx-errors.js` refuses a non-HTML error body), so the target keeps its old content and the user sees nothing; answer errors through `errorpage` or `toast`. Every error renders under its field with `aria-invalid` and once more in the error banner at the top ("Please fix the N errors below."). On success the handler saves and redirects (303, or an `HX-Redirect` header with an empty 200 for an htmx submit) and renders no success message. `Field.Validate` is a URL: the control gets `hx-post`, `hx-trigger="blur changed"` (`change` for select, checkbox, radio, toggle), `hx-target` on its feedback slot and `hx-params={Name}`, so even inside a form only that field's name=value is posted; the handler reads `r.FormValue(name)` and its whole body is `formfield.RespondFeedback(w, r, field, msg)` (empty msg renders the empty slot, status 200 either way: a field's feedback is not an error response).

**Feedback:** every way a handler talks back after an action is one call. `toast.Send(w, r, toast.Error(title, body))` is for htmx responses: it appends the toast out of band to `#toast-container` after the handler's own fragment (setting Content-Type only if nothing has) and writes nothing for a non-htmx request; `toast.Respond(w, r, status, p)` makes the toast the whole answer to a failed action (`HX-Reswap: none`, the status, the toast). `flash.Error(w, r, title, body)` (or `flash.Set`) is for redirects: the handler sets the cookie, redirects, and the shell renders the banner once in `#wf-flash` on the next page and clears it in that render; the wiring is one line, `App.Flash = flash.Take`. A fragment render (`Render`/`RenderParts` for a plain htmx request, body-only or part-only) also consumes a pending flash and appends `<div id="wf-flash" hx-swap-oob="true">…</div>` after the fragment, so a flash set by an htmx action, or by a redirect htmx followed as XHR, shows on the page the user is looking at instead of some later full page; `RenderBare` never calls `App.Flash`. A handler answering an htmx action with a flash should still prefer `HX-Redirect` for a full navigation. Errors first: `Error` and `Warning` are the obvious constructors in both packages; `Success` exists but is opt-in and discouraged under the no-success-messages rule (the re-rendered page is the confirmation), and the Items demo never flashes or toasts on success. `action.Confirm` on any `Action` emits `hx-confirm={Message}` plus `data-wf-confirm-title`/`-label`/`-cancel` and `data-wf-confirm-destructive` (for `VariantDestructive`); `static/js/confirm.js` (first in `appshell.Scripts`) intercepts `htmx:confirm`, fills the page's `#wf-confirm` dialog (`confirmdialog.Host`, rendered by `Document`), focuses Cancel, issues the request exactly once on Confirm and nothing on Cancel/Escape/backdrop, and returns focus to the trigger; without the host or `dialog.min.js` the browser's native `hx-confirm` box runs. Loading: `skeleton.*` holds the final height of a known shape (a table of n rows, a tile, a card, a paragraph); `spinner.Spinner{Indicator: true}` is the `htmx-indicator` for a request with no known shape.

App pattern: configure one `appshell.App`, wrap the mux in `App.Middleware`, render each page with `App.Render`:

```go
var App = &appshell.App{Name: "Demo", HomeHref: "/", Flash: flash.Take} // Flash: the one-shot flash the shell renders in #wf-flash
App.OnPanic = errorpage.PanicHandler                       // a recovered panic answers with the styled 500 (default: a bare one)
App.Palette = &commandpalette.Props{Items: items}          // mod+k and the shell's Search button open the palette on every page
http.ListenAndServe(addr, App.Middleware(errorpage.Handler(mux))) // Handler: the mux's plain 404/405 become errorpage pages
err := App.Render(w, r, "Showcase", pages.Showcase()) // body only for a plain htmx request; full page otherwise, including boosted links and history restores
err = App.RenderBare(w, r, "Sign in", page)             // the Document with no Shell (authpage.Respond uses it); appshell.RenderBare(w, r, name, title, body) does the same with no App
err = errorpage.NotFound(w, r)                          // 404 inside the shell when an App is in the context, bare otherwise; mux not-found handlers use it
// named swap regions (what listpage.Respond and formpage.Respond do):
err = App.RenderParts(w, r, "Items", page, map[string]templ.Component{"items-results": results}) // a plain htmx request whose HX-Target is "items-results" gets only that part
```

`appshell.Must(ctx)` returns the `App` stored by `Middleware` or an error naming `Middleware`; page types call it from their `Respond`. `App.Right` renders in the topbar's right group, before the user menu.

**`assets`** embeds `static/`: `assets.Mount(mux)` serves it, `assets.Handler()` returns the handler, `assets.URL(path)` builds a URL.

**`wflint`** (`internal/wflint`, run via `cmd/wflint`) lints app code (`.templ`, Go, CSS) and rejects raw block HTML, `class`, `style`, `<style>`, `Class:` in Props literals, class/style attribute maps, `templ.Raw`, Go string literals holding HTML markup (`html-from-go-string`), and Alpine class/style bindings. Only text-level elements and component calls are allowed: `p, a, span, strong, em, b, i, code, kbd, br, ul, ol, li, time, small, sup, sub`. `img` is not among them (batch 2): an image is a sized block of content, not a word in a sentence, so app code declares it through `image.Image` and the hint says so. Allowed attributes on those elements are `href, src, alt, title, id, name, datetime, target, rel, download` plus `aria-*`, `data-*`, `hx-*`, `x-*`; `download` was added in batch 2 (a link can sit inside a sentence and downloading is behavior, not design), while `role`, `tabindex`, `width`, `height` and `loading` stay forbidden (something focusable with a role is an interactive thing, and interactive things are components; sizing and loading belong to `image`). The `html-from-go-string` rule was tightened in batch 2 so usage text does not trip it: a `class`/`style` attribute inside a Go string is reported only with a quoted value (case-sensitive, so `"class=%s"` in a log line and `"style= ?"` in SQL pass), and a forbidden opening tag only when the same literal also holds a closing tag (`</`), a quoted attribute value (`="`), or a tag directly after another (`><`), so `"<input> is not allowed"` and `"<div> → layout.Stack"` pass while `"<div class=\"x\">"` and `"<table><tr>"` fail. The sole exemption is a `CustomPage` or `CustomBlock` fence, which needs a written reason; the lint prints every fence on every run. Flags: `-json` for a JSON report; exit 1 on violations, 2 on bad usage. `make check-ui` runs `go run ./cmd/wflint ./demo` and is part of `make check`. The demo runs on the shell and passes with zero fences.

Known lint gaps (not detected today):

- `p.Class = "..."` and `attrs["class"] = ...` assignments; only `Class:` in a Props literal and `"class"` keys in an attribute-map literal are caught.
- Go expressions in `if`/`for`/`switch` conditions of a `.templ` file are not scanned for `templ.Raw` and the other Go-side rules.
- A fence `Reason` must be a double-quoted string literal; a named constant or a raw (backquoted) string is reported as a missing reason.
- `*_test.go` files are exempt from `html-from-go-string` by design (tests assert on rendered HTML).

### The rule for app code

App code never contains anything below the component boundary (no div, no class, no layout decision); composition means choosing and ordering components. The only place that boundary may be crossed is inside a CustomPage or CustomBlock, which must carry a written reason and is printed by every build. A missing component is never a reason to use the fence: stop and file it against webframe.

### CSS source pinning

`static/css/input.css` uses `@import "tailwindcss" source(none)` and pins sources to `components/**/*.templ` and `demo/**/*.templ` (demo Go code holds no class strings; the wflint `html-from-go-string` rule keeps it that way), so markdown and JS can never change `output.css`. Class-less text gets element typography from `:where(.wf-content)` rules there.

Legacy consumer classes: three older apps still write Tailwind classes in their own `internal/web/**/*.templ` files, and `source(none)` no longer scans them. `input.css` keeps them compiling with one `@source inline("...")` line under the "Legacy consumer classes" heading, listing every token those apps use (in `class="..."` attributes and `Class: "..."` Props literals) that is not otherwise in `output.css`. Remove an app's tokens when that app migrates to `appshell`; delete the line when all three have.

## Conventions

- Always commit `*_templ.go` when `.templ` files change — reviewers need to see generated HTML
- Keep components additive; don't break existing Props contracts
- Tests are render-focused: render to `bytes.Buffer`, assert on HTML string content
- Chart components (barchart, piechart, areachart, sparkline, metricring) are SVG-based, accept `float64` values, and sanitize color inputs
- `components/render_smoke_test.go` has one table row per `components/` directory; adding a component package without a row fails the test
